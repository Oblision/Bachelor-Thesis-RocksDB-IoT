Out-of-Core Stream Processing in NebulaStream

Spilling tumbling windowed-aggregation state to RocksDB so a query whose state exceeds RAM completes instead of being OOM-killed — design, implementation, and evaluation.

The problem and the goal

Motivation

NebulaStream (NES) is a push-based stream processor. A windowed aggregation such as GROUP BY key WINDOW TUMBLING keeps one hash map of partial results per window in memory. For long windows or many distinct keys — think city-scale IoT sensor streams — this state can grow larger than RAM, and the engine is OOM-killed.

The slice store holds the live aggregation state. When that state > RAM, the process dies.

The goal (success gate §3.3)

Process tumbling-window state that is larger than physical memory, without OOM, by spilling cold state to disk (RocksDB) and bringing it back only when a window must emit its result.

Three research questions

  • RQ1 — integration: how to fit an out-of-core (OOC) backend into the push-based model.
  • RQ2 — performance: throughput and tail latency (p95/p99) of a research-informed RocksDB configuration for tumbling OOC.
  • RQ3 — efficiency: how CPU, disk I/O and storage (write amplification, footprint) scale as state grows past memory.
Scope locked by the signed proposal (§2.3.2) Tumbling windows only · no sliding windows · no variable-sized serialization · no Nautilus JIT / codegen edits. Every mechanism in this work is therefore host-side.

The system we built

Architecture

The spill machinery slots in underneath the existing slice store, so the query operators above it are unchanged. Four pieces work together:

  • SpillConfig — the knobs (thresholds, RocksDB sizes, partitions, emit lag).
  • SpillBackend — a storage interface with three implementations: Null, InMemory, and RocksDB (durable, lz4-compressed).
  • SliceSerializer — turns a window's chained hash map into a flat byte record and back (fixed-size entries).
  • Spillable slice store — owns the backend and runs a background spiller thread that evicts cold slices under memory pressure.

Soft threshold wakes the background spiller; hard threshold forces a synchronous spill. Cold (completed, not-yet-emitted) slices are the spill target — never state already handed to the async probe.

What happened: three discoveries

The story

Getting OOC to actually work was not one step — each fix revealed the next, deeper bottleneck. This is the heart of the project.

1

“Cold equals emitted” — nothing spilled

The first real query spilled 0 bytes. In tumbling windows a slice becomes cold and emitted in the same step, so the “cold and not-yet-emitted” set the spiller looks for is always empty.

Fix → emit-decouple: a lagged emit watermark (emit_lag) retains a band of completed-but-unemitted windows, which are now spillable.
2

Terminal-flush re-materialization — config can’t win

Now the query spilled (45 MB), yet spill-ON and spill-OFF still died identically at tight caps. The real cause: at end-of-stream the retained band must re-materialize into RAM in one burst to emit — no matter where it was stored. First clean measurement: process peak 417 MB while the store itself was only ~20 MB.

Insight → the burst, not the threshold, is the enemy. Tuning cannot fix it.
3

Bound the burst

Phase 1 paces the flush (emit one window at a time, free before the next). Phase 2 partitions each window so only a fraction is ever resident — the contribution on the next page.

Result → the terminal burst shrinks from “whole band” to “one partition.”
Why this matters for the thesis narrative The honest finding is that naive OOC does not solve the OOM on its own — the terminal re-materialization burst defeats it. The contribution (page 4) is what makes OOC viable.
4

Partition-at-spill — the contribution

Core idea

The idea is textbook grace-hash / external aggregation (Shapiro 1986; used by Postgres, DuckDB, Spark). At spill time, split a window’s hash map by hash(key) % P into P self-contained blobs. At emit time, stream one partition back at a time — so read amplification is 1× and resident memory is only 1/P of the window.

// at spill: route each entry to one of P self-contained blobs
partition = hash(key) % P;                 // keyed (sliceEnd, worker, partition)
// at emit: only NON-EMPTY partitions are streamed, contiguously renumbered
//   (an empty chunk would crash the un-editable Nautilus probe — audit catch)

Correctness: with P=1 the path is byte-identical to the in-memory engine; a differential test shows P=1 vs P=8 produce byte-identical output (50 020 rows) — partitions are key-disjoint and complete.

Headline result — 320 MB cap, 4 threads Naive OOC (P=1) is OOM-killed; partition-at-spill (P=8) completes, with the slice-store working set dropping from the whole band (~78 MB) to ~4 MB — the 1/P bound.
5

Evaluation

Measurement

To answer RQ2/RQ3 we added production-visible, grep-parseable metrics emitted at query stop: spill/restore counts + bytes + latency (including the partitioned read-back), RocksDB write-amplification + on-disk footprint, and per-task p50/p95/p99. The unit-test suite is at 893/893 (+18 new). The sweep ran 105 capped Docker runs over a state ladder × {320, 512 MB} × variants × 3 reps (throughput CV 0.005–0.079, so 3 reps suffice).

Honest caveats

  • Latency is per-task, not per-window (the engine exposes only per-task events); percentiles are unreliable for very small sample counts.
  • Enabling RocksDB Statistics adds a few % Put-path overhead — constant across cells, so comparisons hold.
  • The in-memory baseline survives at these state sizes; the OOM that partitioning solves is the OOC terminal re-materialization burst (naive P=1), not raw in-memory fit.
  • Process RSS is dominated by the fixed buffer pool; store_peak is the metric partitioning controls.
Bottom line Partition-at-spill turns naive OOC — which OOMs on the terminal flush — into a system that completes tumbling windowed aggregation with state spilled to RocksDB, at ~8% throughput overhead, write-amp 1.0, and a store working set bounded to ~1/P. The §3.3 gate is met and RQ1–RQ3 are answered; the engineering is committed and ready for the thesis write-up.
