## Executive summary

We implement **partition-at-spill** (grace-hash "Option b"): at spill time the already-built per-worker `ChainedHashMap` is split host-side by `hash % P` into `P` self-contained NSS1 blobs, each written under an extended RocksDB key `(sliceEnd, worker, partition)`; at emit time each partition is read back **whole, with no filtering**, so the spilled state is read back at `1/P` granularity and total payload bytes written are unchanged (write-amp is only `P × 40B` headers per worker). This is textbook external/grace-hash aggregation (Shapiro 1986, Graefe 1993) adapted to a streaming tumbling-window slice store, and it explicitly **supersedes partition-at-read** (the FEASIBILITY "Option a"), which would have paid `P×` read amplification on every emit — unacceptable on a constrained device. The split is HOST-ONLY post-hoc: **no Nautilus/JIT/codegen edits, no insert-time hash routing, no sliding windows, no variable-sized serialization.** `number_of_partitions = 1` is the default and takes a fast-path bypassing partitioning entirely, behaviorally identical to today. The build sequence is **2a → 2e**, pure/isolated first (serializer, backend key, slice primitive) and the concurrency-sensitive store last, each gated at **≥ 835 tests**. The async-in-flight pileup (FEASIBILITY "THE NUANCE") is bounded only at the build side by partitioning; a hard process-peak bound, if still needed after measurement, is delivered by **2e: a counting-semaphore token pool sized to `N ≥ 2` in-flight chunks** — framed for the thesis as "Flink's credit model at coarser (partition) granularity." 2e is **CONDITIONAL** on the 2d measurement still OOMing.

## 1. Decision record

**Chosen: partition-at-spill (grace-hash, "Option b"). Partition-at-read ("Option a", FEASIBILITY §Gate 2) is SUPERSEDED.**

Rationale: partition-at-spill pays the partitioning cost **once at write time** (re-keying the same entries into `P` blobs; total payload bytes written are unchanged — only `W·(P−1)·40B` of extra headers, `PARTITION-AT-SPILL.md:170`), and is **write-neutral on payload**. In exchange, every emit reads each partition back exactly once (`1×` read-amp, `1/P` of the data resident per chunk, `PARTITION-AT-SPILL.md:171-174`), because a partition blob is a complete NSS1 record that `SliceSerializer::deserialize` reads whole with no filtering. Partition-at-read does the opposite — one blob per worker, but each of `P` emit passes deserializes the full worker blob and discards `(P−1)/P`, i.e. `P×` read amplification and `P×` transient decompression on every emit. On the constrained-device target, spilled state is read back at least once, so paying `P×` on the read path is the wrong trade; pre-partitioning at spill is the correct one. This is exactly the **textbook grace/hybrid-hash discipline** ("partition so each piece fits, process one partition at a time" — Graefe 1993 §3.2; Shapiro 1986 hybrid hash), used today by PostgreSQL v13 hashagg, DuckDB radix aggregation (ICDE 2024), Spark, and Trino; our contribution is adapting it to a streaming tumbling-window slice store on memory- and IOPS-constrained hardware. The FEASIBILITY findings that **remain valid and are carried forward unchanged**: the multi-chunk emit correctness gate (key-disjoint chunks ⇒ each key emitted once; `chunkNumber=INITIAL+p`, `lastChunk=(p==P-1)`; precedent `StreamJoinOperatorHandler` emits N² chunks/seq today), the async-in-flight "NUANCE" (build-side bound ≠ process-peak bound), and the differential `P=1` vs `P>1` correctness gate.

## 2. LOCKED decisions

The following are decided. Downstream agents MUST treat these as intentional and MUST NOT flag them as bugs or re-open them. (Hard constraints from the task — no JIT/codegen, no sliding windows, no variable-sized serialization, `P==1` byte-identical, manual push policy, regression ≥ 835 — are pre-locked and assumed throughout.)

**L1 — P==1 fast-path (bypass partitioning entirely).** When `number_of_partitions == 1`, both `spill` and the emit path call the *existing* `SliceSerializer::serialize` + a single `put(..., p=0, record)`, and emit one chunk/window exactly as today. Chosen over "make the `p==0` key equal the old 12-byte key" because the latter forces the key encoder to branch on `p` and special-case the prefix-sweep boundary — more code, sharper edge — for an on-disk wire-compatibility property nothing in scope needs (the spill store is transient `/tmp` scratch, recreated per query). Rationale: `PARTITION-AT-SPILL.md:130-136`.

**L2 — `PartitionId` = `uint16_t`; suffix goes AFTER the worker bytes.** The RocksDB key becomes `<sliceEnd:8 BE><worker:4 BE><partition:2 BE>` = 14 bytes (`KEY_BYTES = 14`). `uint16_t` (P ≤ 65535) is ample for an edge device and keeps the key narrow. Critically, **`slicePrefix` stays the 8-byte `sliceEnd` prefix** (confirmed `RocksDBSpillBackend.cpp:58-65`), so `erase(SliceEnd)`'s prefix sweep still collects every `(worker, partition)` record of the slice with no change; placing partition after worker also keeps one worker's partitions key-contiguous (incidental locality, not required). Use a strong typedef or a plain `uint16_t`; default the parameter to `0` so non-partitioned callers stay source-compatible. Rationale: `PARTITION-AT-SPILL.md:65-67`.

**L3 — Empty-partition policy: SKIP-EMPTY at write, ⚠️ REVISED 2026-05-24: SKIP-EMPTY + CONTIGUOUS-RENUMBER at emit (was: always-emit-chunk-p).** On the **write** side, `spill` does not `put` a partition blob that contains zero entries for that worker (leaner for constrained flash; `get` returning `nullopt` is already tolerated exactly like a never-created worker map, `SpillableAggregationSlice.cpp:131`). On the **emit** side, the ORIGINAL plan was to always emit chunk `p` for every `p ∈ [0,P)` (with `numberOfTuples=0` for empty partitions) so `chunkNumber=INITIAL+p`/`lastChunk=(p==P-1)` were correct by construction. **The 2d architecture audit (`arch-2d`, PLAN-2d) found this UNSAFE: a 0-tuple chunk has `finalHashMapPtr == nullptr`, and the Nautilus `AggregationProbePhysicalOperator::open` iterates `finalHashMap` unconditionally (`AggregationProbePhysicalOperator.cpp:133` → `ChainedHashMapRef::begin()` → `ChainedHashMap::getPage(0)` PRECONDITION), which terminates on a null/empty map. At P=1 this never fires because every triggered window is non-empty so the combined `finalHashMap` always has ≥1 page; an empty partition chunk at P>1 is a genuinely new case. The probe is traced/JIT code and the no-JIT constraint is LOCKED, so it cannot be guarded.** REVISED policy (no-JIT, handler-side): **emit only the `K` NON-EMPTY partitions, renumbered CONTIGUOUSLY `chunkNumber ∈ [INITIAL, INITIAL+K-1]`, `lastChunk` on the `K`-th (the highest-numbered)**. `ChunkCollector::Chunk::update` (`ChunkCollector.hpp:81`) completes a sequence iff the last chunk's 0-based number equals the count of non-last chunks (last does `fetch_add(chunk)`, non-last `fetch_sub(1)`, complete at counter 0), so `K` contiguous chunks complete correctly WITHOUT `P` being known downstream, and every emitted chunk has ≥1 entry (matching the probe's implicit P=1 invariant) → no empty map ever reaches the probe. Degenerate fully-empty window (`K==0`, which does not arise for a triggered window since triggered windows have data) falls back to the P=1 single-chunk emit, byte-identical to base. The differential P=1-vs-P=8 gate (§7) proves output is unchanged (same rows, no dups/drops — `K` chunks vs 1 chunk is a chunk-count difference only, not a row difference). Rationale: `PARTITION-AT-SPILL.md:94,210`; chunk metadata `FEASIBILITY.md:13-16`; revision evidence `PLAN-2d.md` + arch-2d O1 analysis.

**L4 — `partitionedSerialize` is TWO-PASS (count, then write).** Pass 1 walks the chain counting entries per partition (`hash % P`); allocate `P` `SpillRecord`s; write each header with that partition's own exact `numEntries`. Pass 2 walks again appending `[hash][payload]` to `record[hash % P]`. `entrySize/pageSize/numberOfBuckets` are identical across all `P` blobs (same map layout); only `numEntries` differs. Chosen over single-pass back-patching the `numEntries` header field: two-pass is simpler, gives exact `reserve()` and an exact per-partition header, and the count walk is cheap CPU versus the I/O. Each `record[p]` is byte-for-byte a valid NSS1 record indistinguishable from `serialize` on a map containing only that partition's entries. Rationale: `PARTITION-AT-SPILL.md:88-90`.

**L5 — Atomicity of the P puts: SEQUENTIAL puts with free-after-loop + erase/retry safety net (WriteBatch noted as future hardening).** `spill` issues `P` separate `backend.put` calls, then flips `resident=false` and `reset()`s the maps **only after the full P-put loop succeeds** (mirroring today's order at `SpillableAggregationSlice.cpp:112,116`). On a throw mid-loop, the `ReservationGuard` releases the reservation and the partial on-disk blobs are orphaned but harmless — overwritten on retry (same keys) or dropped by `erase` at GC. Trade: the `P` puts are not a single atomic durable group, so a crash between puts leaves partial blobs (acceptable: spill store is transient, recreated per query). Wrapping the `P` puts in a RocksDB `WriteBatch` (the backend already uses `WriteBatch` for `erase`, `RocksDBSpillBackend.cpp:175`) is a cheap robustness add and is **recommended but NOT required** for the demo; document it as future hardening. Rationale: `PARTITION-AT-SPILL.md:149`.

**L6 — Scope: TERMINAL-emit path is partitioned; steady-state stays P=1 for now.** Partition-at-spill emit is wired into the **terminal flush** path (`triggerAllWindows` → `ensureWindowSlicesResident`/`getAllNonTriggeredSlices`). The steady-state path (`getTriggerableWindowSlices`, `SpillableTimeBasedSliceStore.cpp:366`) keeps the whole-window P=1 emit until measured, because steady-state partition-emit would interact with `pinnedKeys`/late-write (Increment C) and may emit a slice before it is fully cold. **Note:** the *spill write* always writes P blobs when `P>1` regardless of which path later emits them — only the *emit loop* is terminal-first. Rationale: `PARTITION-AT-SPILL.md:212`; blast table `:25`.

**L7 — Default P: ship a FIXED `number_of_partitions` config knob; auto-sizing is documented future work.** For Phase 2 we ship `SpillConfig::numberOfPartitions` (`UIntOption`, default `"1"`); the demo sets it to e.g. `8`. We **explicitly do NOT** implement the size-driven auto-sizing formula `next_pow2(clamp(⌈1.5·S/B⌉, 4, P_max))` from `EXTERNAL-AGG-AND-FANOUT.md` R.1 for Phase 2 — it is the right *future* enhancement (measure `S` at spill time, the map already exists, so we can do better than Postgres which estimates pre-build), but a fixed knob is the simplest thing that ships and isolates the partitioning mechanism from a sizing policy. **L8 — Ownership/2c: `EmittedAggregationWindow` owns the per-worker partition maps. ⚠️ REVISED 2026-05-24 by the lifetime totality audit (`exploration/EMITTEDWINDOW-LIFETIME-AUDIT.md`, VERDICT: RED-as-written → YELLOW-with-guardrails).** The re-materialized partition maps in `streamEmitByPartition` are freshly deserialized and **NOT slice-owned** (the slice stays spilled), so `emittedKeys`/GC do not keep them alive. ## 3. The 2e backpressure design (CONDITIONAL)

**Status: NOT TRIGGERED → NOT BUILT (measured 2026-05-25). CONDITIONAL design retained as available-if-needed future work.** The §7 trigger run (320 MB cap, threads=4) returned **P=1: rc=137 (OOM-kill); P=8: rc=0, store_peak=4 MB ≪ 78 MB** — partition-at-spill alone bounded the process, so 2e is NOT built (see `exploration/../eval-phase/phase2e/RESULTS.md`). The shape below is LOCKED *if 2e is ever triggered* by a future workload/config; whether it is triggered is decided empirically (see trigger below and §7).

**Why it may be needed.** Partition-at-spill bounds the **build-side** working set (each chunk is `≈ B/P`), but emit is **async** (`emitBuffer` queues; the probe drains later), so the *in-flight emitted set* can still pile up to ≈ the whole retained band if the terminate loop outruns the probe — the same failure mode that made Phase 1 neutral (`store_peak` stayed at 78MB, OOM at the 320 cell even at threads=4). Partitioning mitigates this two ways (smaller in-flight units; production is RocksDB-I/O-gated per partition so a fast probe at threads>1 is likelier to keep up) but does NOT alone bound the in-flight **count**. Rationale: `FEASIBILITY.md:28-37`, `PARTITION-AT-SPILL.md:178`.

**The mechanism (LOCKED shape).** A bounded in-flight-chunk **token pool** = a counting semaphore `inflight` initialized to `N` (`std::counting_semaphore`-style), where one permit = the right to have one emitted re-materialized partition/chunk outstanding in the async finalizer's queue. Equivalently a bounded blocking queue of capacity `N` between the terminate loop and the probe.

- **Producer (terminate/replay loop):** `inflight.acquire()` (blocks if `N` chunks already outstanding — this *is* the backpressure: the producer blocks instead of starving the buffer pool / OOMing) → read the next spilled partition from RocksDB and re-materialize it → **push** the chunk to the async finalizer → loop.
- **Consumer (async JIT probe):** after it has **fully consumed a chunk's buffers and freed them back to the pool**, call `inflight.release()` (one permit per completed chunk). The release is what unblocks the producer.
- **acquire/release placement (critical):** `acquire` is **before** producing the unit (never over-produce). `release` is **after** the consumer has *freed the buffers* — NOT on enqueue and NOT when the probe task is merely scheduled. Releasing on enqueue defeats the bound (the producer refills while memory is still resident). The permit tracks **memory liberation**, mirroring Flink where a credit returns only when the receiver's buffer is actually free. The natural seam is the same host cleanup lambda that frees `ownedPartitionMaps` (L8) — release the permit there, RAII-guarded.

**Sizing N.** `N = floor(emit_memory_budget / max_partition_footprint)`, with `N ≥ 2`. `max_partition_footprint` = one chunk's re-materialized buffers plus the finalizer's transient working set for that chunk. `P` is chosen large enough (L7) that each chunk is small enough for `N ≥ 2` to fit — this is *why* partitioning matters: it shrinks the unit so a meaningful `N` fits. `N` is the explicit memory/throughput knob (the coarse analogue of Flink's `buffers-per-channel`): larger `N` = more pipeline overlap, higher peak; smaller `N` = tighter memory, less overlap.

**Liveness conditions (LOCKED invariants).**
1. **Drain on a different thread than the terminate loop (threads > 1).** If the probe drains inline on the terminate thread, the thread that must `release` is the very thread parked in `acquire` → self-deadlock. Either run the finalizer drain on a distinct worker thread, or use non-blocking `try_acquire` + cooperative reschedule (never a hard park that monopolizes the only worker).
2. **RAII / exception-safe release.** Every `acquire` matched by exactly one `release`, including the error/abort path, via scope-guard — a leaked permit shrinks effective `N` until the pipeline wedges.
3. **Consumer working set reserved OUTSIDE the N budget.** The buffer pool must have headroom > 0 beyond the `N` in-flight chunks so the consumer can always allocate the scratch it needs to *finish* a chunk and thus release a permit. If freeing a permit itself requires allocating from an exhausted pool, the starvation deadlock returns. **Invariant:** at least one outstanding chunk can always be finished using memory outside the `N`-token budget.

Hysteresis (high/low watermarks, Storm/Heron-style) is optional and only warranted if profiling shows thrashing — a partition-granularity semaphore oscillates far less than a per-buffer one, so a plain counting semaphore suffices.

**Thesis framing:** this is **push-native and not a hack** — it is **Flink's credit model at coarser (partition) granularity** (1 token = 1 in-flight partition, instead of 1 credit = 1 network buffer). The honest caveat: unlike Flink/Storm, NES core provides no framework-level backpressure, so we implement the bound **locally at the spill-emit seam** as a single-process counting semaphore.

**Trigger (the exact measurement that decides whether 2e is built):** run `run-rss.sh` on the 320 cell at **threads > 1** with **P > 1** (see §7). **Build 2e iff** the run returns `rc = 137` (OOM-kill) **or** `store_peak ≈ the whole retained band` (i.e. partitioning alone did not bound the process peak). If 2d already gives `rc = 0` and `store_peak ≪ 78MB`, 2e is **not built** for Phase 2 (note it as available-if-needed in the thesis).

## 4. Skew (LOCKED position)

**Correctness is unaffected by skew; the `1/P` memory bound degrades under adversarial single-key skew. Documented as a known limitation; recursive/adaptive repartition is future work.**

`hash % P` is uniform only if the (MurMur3) hashes are well-distributed across residues, which holds for typical IoT keys but not adversarially. Worst case (all keys collide mod P, or a single dominant key): one fat partition's footprint ≈ the whole window and the `1/P` bound degrades toward `1`. This is acceptable-with-caveat for the demo because: (a) **every key is still emitted exactly once** — correctness is independent of the partition distribution; (b) the average case on real IoT keys is near-uniform; (c) the spill side writes the same total payload bytes regardless of skew. A skew-robust split (range-balanced assignment, splitting the fat partition, recursive repartition consuming fresh hash bits) would not change the host-only/no-JIT property and is named future work.

**Citable framing (thesis):** "`hash % P` only bounds per-partition memory when group-key *frequencies* are not pathologically concentrated. A good mixing hash makes partitions uniform under moderate frequency skew, but a single dominant key maps its entire mass to one partition, which no static fan-out can bound — the same limitation acknowledged by production engines (e.g. Trino: spilling *may fail to divide intermediate data into chunks small enough … leading to out-of-memory* [S15]). Our single-pass, fixed-stride design assumes bounded single-key mass; recursive repartitioning (Graefe 1993 [S2]; PostgreSQL `used_bits` recursion [S4]) is the graceful-degradation fallback, and runtime-adaptive repartitioning / bucket-spreading (Nakayama–Kitsuregawa–Takagi 1988 [S10]; Kitsuregawa–Ogawa 1990 [S12]; Spark AQE skew handling [S14]) is out of scope and noted as future work." (Source: `EXTERNAL-AGG-AND-FANOUT.md` R.2, §B.4.)

## 8. Thesis-ready paragraphs

### 8a. External-aggregation "textbook best practice" framing

> External (out-of-core) hash aggregation by **partitioning so that each partition's hash table fits in memory, then processing one partition at a time** is the established technique for memory-bounded grouping, going back to hybrid-hash join (Shapiro 1986 [S1]) and codified in Graefe's survey (1993 [S2]). It is the mechanism used by every mature analytical engine that supports spilling GROUP BY: PostgreSQL's disk-based hash aggregation ([S4]–[S6]), DuckDB's radix-partitioned external aggregation (Kuiper, Boncz, Mühleisen, ICDE 2024 [S7]), Spark SQL's shuffle + external aggregation [S13], and Trino's spilling aggregations [S15]. This thesis adapts that established technique to a streaming tumbling-window *slice store*: at spill time the in-memory aggregate map is partitioned by `hash % P` into *P* independently emittable on-disk blobs, bounding resident state to *O(M)* regardless of window-state size. The partition count follows the size-to-fit rule of Graefe (1993) with PostgreSQL's 1.5× headroom factor [S6] — `P = next_pow2(clamp(⌈1.5 · S / B⌉, 4, P_max))` for measured spilled-state size *S* and per-partition budget *B* (presented as the principled auto-sizing path; the Phase-2 prototype ships a fixed `number_of_partitions` knob and defers auto-sizing to future work). The streaming precedent is Flink's RocksDB state backend, which keys disk-resident window state by `<KeyGroup, Key, Namespace>` (namespace = the window) and reads back only the relevant per-window entries at fire time [S21][S23]; NebulaStream currently has **no spillable state backend**, so a window larger than RAM OOMs — the gap this thesis closes for **memory- and IOPS-constrained edge devices**, where the production backends' assumptions (server RAM, fast NVMe, runtime-adaptive repartitioning) do not hold. On constrained flash we store **one RocksDB key per partition** (large sequential value) rather than per group, to minimise key count, write amplification, and compaction churn [S18]–[S20].
>
> *Key citations:* Shapiro 1986 (TODS) [S1]; Graefe 1993 (ACM Computing Surveys) [S2]; PostgreSQL v13 hashagg `nodeAgg.c` [S4][S6]; Kuiper/Boncz/Mühleisen ICDE 2024 [S7]; Flink RocksDB state backend [S21][S23]; RocksDB amplification [S18][S19].

### 8b. Push-based backpressure framing

> The de-facto best practice for backpressure in **push-based** stream processors is to **bound the number of in-flight units** between a producer and a (possibly asynchronous) consumer, and to **throttle the producer** when that bound is reached — without ever inverting control flow to a pull/demand-driven model. This is realised in production engines as either a **credit / token budget** or an equivalent **bounded queue with high/low watermarks**. Apache Flink exemplifies the credit form: its runtime still *pushes* result buffers downstream, but a sender "must never send buffers without credit," where each credit is a buffer slot the **receiver has guaranteed** — so credits bound the in-flight buffer count and propagate backpressure upstream while keeping the engine push-based [1][2]. Apache Storm's `topology.max.spout.pending` is the same idea at tuple granularity (a bounded pool of un-acked tuples that gates the spout) [4], and Storm 1.0 and Heron add bounded receive queues with watermark hysteresis [6][8]. The underlying primitive is the classic **bounded buffer / counting semaphore** producer-consumer pattern [14][15], standardised for asynchronous pipelines by **Reactive Streams** non-blocking backpressure (`request(n)`) [16]. For the out-of-core spill-emit path, the external-memory classics already prescribe a **partition-at-a-time, bounded-resident discipline** (Shapiro's hybrid hash [17]; Graefe's survey [19]); we extend that discipline across an *asynchronous* finalizer by adding a **counting semaphore sized to N in-flight partitions** — acquire a token before emitting a re-materialized partition, release it when the finalizer has consumed and freed that chunk. This is **push-native and not an ad-hoc workaround: it is precisely Flink's credit model at a coarser (partition) granularity.** The honest caveat is that, unlike Flink or Storm, **NES core provides no framework-level backpressure**, so we implement the bound **locally, at the spill-emit seam**, as a single-process counting semaphore (token = one outstanding partition), with the liveness requirement that the finalizer drains on a separate thread (threads > 1) so a blocked producer cannot starve its own consumer.
>
> *Key citations:* FLINK-7282 credit-based flow control [1] + Flink network-stack blog [2][3]; Storm `max.spout.pending` [4] and STORM-886 watermark backpressure [6]; Heron stream-manager backpressure [8][9]; bounded-buffer / counting-semaphore [14][15]; Reactive Streams spec [16]; Shapiro 1986 [17]; Graefe 1993 [19].

> Full citation lists live in `exploration/PUSH-BASED-BACKPRESSURE.md` (Sources) and `exploration/EXTERNAL-AGG-AND-FANOUT.md` (Sources). Two skew papers (Nakayama 1988 [S10], Kitsuregawa/Ogawa 1990 [S12]) and the Heron SIGMOD 2015 watermark quote need a verified primary PDF/DOI before final thesis submission.
