4 — Write Stalls: Compression + Write Buffer Interaction

Methodology note: db_bench only reports stall statistics when stalls actually occur. Runs with no stall data had zero stalls. The initial analysis overestimated the mean stall rate by sampling only slow, stalling runs. The corrected analysis treats missing stall data as 0%.

Left: Corrected stall % vs write buffer size by compression. Right: Stall % heatmap (compression × wbuf). Larger buffers do reduce stalls dramatically — but only with compression enabled.

Fraction of runs experiencing any write stall. At 4 MB wbuf, 100% of runs stall regardless of compression. With lz4 at ≥16 MB, fewer than 10% experience stalls.
Larger buffers DO reduce stalls: 4 MB → 30% mean, 16 MB → 3.9%, 64 MB → 1.3%, 128 MB → 0.0%.
Without compression, stalls persist at all buffer sizes. At 32 MB wbuf: none = 25.5%, lz4 = 0.1%. Uncompressed SST files are larger, so compaction moves more data and falls behind.
32 MB anomaly with none: flush produces large L0 file exceeding L1 target size, forcing full-overlap compaction rewrite.
zstd at 4 MB is worst of all (52.9%): high CPU cost slows flushes/compaction; with tiny buffer, flushes outpace compaction.
Corrected NebulaStream implication: With lz4 compression and ≥16 MB write buffer, stalls drop below 1% — the combination effectively eliminates the stall problem. The earlier “23% stall rate” was a sampling artifact from missing-data bias.

Stall Mitigation: Proposed Follow-Up Sweep

The corrected stall analysis shows that lz4 + ≥16 MB wbuf already reduces stalls below 1%. However, the remaining stalls with none compression and small buffers are still severe, and two stall-related parameters were fixed in this sweep: max_write_buffer_number=2 (only 1 active + 1 flushing — zero queue depth) and level0_slowdown_writes_trigger=20. A follow-up sweep can quantify whether these knobs further reduce stalls in the remaining problematic configurations.

Mitigation Levers

#LeverMechanismTradeoff
1 Increase max_write_buffer_number (2→3–4) Adds queued memtables to absorb flush latency spikes +1–2 × wbuf memory
2 Raise L0 slowdown/stop triggers (20→40–60) Tolerates more L0 files before throttling writes Slightly slower point lookups
3 Lower compaction trigger (4→2) Starts compaction earlier, keeping L0 file count low More frequent small compactions
4 Rate-limited ingestion Real sensors: 1K–10K events/sec vs db_bench max speed None — more realistic
5 Increase background threads (1→2) Overlaps I/O waits with CPU work during compaction CPU contention on single-core
6 FIFO compaction for windowed state Drops old SST files instead of merging — zero write amp No range scan optimization

Fixed: lz4, write_buffer_size=32MB, cache_size=32MB (winners from current sweep)
Why this isn't a dealbreaker: The corrected analysis shows lz4 + ≥16 MB wbuf already achieves <1% stall rate. The remaining problematic configs (no compression, small buffers) can be further improved by tuning the knobs above. Real sensor ingestion at 5K events/sec is also well within even the worst config's capacity (1,587 ops/sec).
