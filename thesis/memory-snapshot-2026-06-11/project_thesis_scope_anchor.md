**⚠️ PROPOSAL RE-READ (2026-06-07) — breadth not depth; emit_lag is NOT in the proposal.** Re-read the signed PDF in full to settle a breadth-vs-depth question:
- **Mechanism is "spill COLD window state" (§3.1, verbatim), triggered by soft/hard MEMORY watermarks.** You can only spill COLD (completed/inactive) windows. A single long HOT (still-building) window is NOT cold → the proposal's own mechanism cannot spill it. So the scope is the BREADTH case (many cold/completed windows), NOT depth (one window > RAM).
- **Depth / sub-window temporal slicing is OUT.** Spilling cold *sub-slices* of a not-yet-closed window is the sliding-window slicing mechanism — and §2.3.2 excludes sliding windows (+ JIT/codegen edits). So "make a long window survivable by spilling its cold parts" is doubly out of scope. (Corrects the older project-ooc-mechanics note "depth out of scope — needs JIT"; sharper reason: mechanism only spills COLD state + sub-slicing = excluded sliding.)
- **emit_lag appears NOWHERE in the proposal.** The large state is meant to come from the WORKLOAD: §3.1 "synthetic workloads generate a tumbling-window state that exceeds available memory under skewed and bursty input patterns." Our entire emit_lag investigation was a PROXY to force cold-window accumulation on the perfectly-ordered lockstep workload (which emits+frees immediately, so nothing accumulates). The proposal-aligned path: skewed/bursty (high-cardinality / out-of-order) workload → many concurrent/cold windows → state > 512MB → memory watermarks spill cold windows → survive. No emit_lag needed.
- **DESIGN CONSTRAINT (the real one):** OOC only rescues an OOM if the over-budget state sits in COLD/COMPLETED windows (spillable). If a single HOT window's cardinality alone exceeds RAM, that's depth → unspillable → neither the proposal's mechanism nor any in-scope option helps. So the eval workload MUST spread state across MANY windows (breadth), e.g. via out-of-order arrival keeping multiple windows open + adequate per-window cardinality.
- **Baseline (§3.3.2) re-confirmed:** standard backend, identical CPU, NO memory limit (the `inmem_uncapped` denominator). OOC-at-512MB vs uncapped-standard = overhead (throughput, p95/p99) + "survives where capped baseline would OOM."

**How to apply:** for thesis eval work, default to synthetic SKEWED/BURSTY workloads (workload-driven large state, NOT emit_lag) + the 5 RQs above + the inmem-no-cap baseline. The OOC value = spilling COLD completed windows (breadth). Do NOT pursue depth/sub-slicing/sliding/Nexmark/cross-system unless the user explicitly elevates it.

**⚓ WORKLOAD REALIZATION + BUILD DECISION (2026-06-07).** Built the proposal-aligned skew/bursty eval. Durable facts:
- **The native NES Generator source CANNOT produce skew.** `NORMAL_DISTRIBUTION` for INTEGER types is actually `std::binomial_distribution` (`nes-plugins/Sources/GeneratorSource/GeneratorFields.cpp:280`) — symmetric, light-tailed, and cardinality grows only ~√n (needs n≈1.5e9 for 100k distinct). `SINUS` rate varies WALL-CLOCK arrival only (not event-time), so it gives bursty ingestion but NOT out-of-order windows. No Zipfian, no disorder injection. ⇒ **skewed/out-of-order workloads MUST be pre-generated to a CSV and replayed via the File source** (CSV, positional cols, streams once then EOF-terminates; path resolves under `nes-systests/testdata/` or absolute `/workspace/...`).
- **Skew tool:** `.planning/eval-phase/lag-validation/work/gen_skew.py` (uses graphify venv `/home/oblision/graphify/.venv/bin/python` for numpy) generates Zipfian keys + out-of-order ts (lateness D) + optional bursts. Workload template `work/genfile.test`; `run-cell.sh` now takes `TEMPLATE=` and `FILECSV=` envs.
- **emit_lag is now PRINCIPLED, not scaffolding, for file workloads:** NES watermark = max-ts seen, retained band = [maxts−L, maxts]. With monotone base-ts + per-row jitter in [0,D], setting **emit_lag = D = allowed-lateness** keeps late rows from being dropped and holds ~D/W windows concurrently open (breadth). So emit_lag = the standard out-of-order tolerance bound, not an artifact. See [[project-ooc-mechanics]].
- **KEY TENSION (quantified):** skew CONCENTRATES state into hot keys → small state; but state>memory needs HIGH cardinality (the cold tail). They fight. To get both, use a large key universe + high per-window density. Empirical recipe at W=50k: keys=1.5M, zipf=1.0, ~180k rows/window → ~48.6k distinct/window with top-10 keys carrying ~20% of traffic (clearly skewed) → ~152 MB band over N_w=80.
- **BUILD DECISION (user, 2026-06-07): debug build NOW for the RQ1 survival contrast, RELEASE build LATER for RQ2/RQ3 perf.** Only `cmake-build-debug` exists (`CMAKE_BUILD_TYPE=Debug`). Debug-build throughput (~19k keys/s) and tail-latency are NOT representative for RQ2 — a release build is REQUIRED before reporting perf numbers. The debug base RSS (~195 MB) also eats 38% of the 512 MB cap, cramping the contrast. Re-elevate the release build when moving to RQ2/RQ3.

**🔑 LOAD-BEARING FINDING — out-of-order makes the lag band HOT/UNSPILLABLE (2026-06-07).** The single most important mechanics result for the eval design:
- OOC spills only COLD (no-longer-modified) windows. With out-of-order arrival and `emit_lag = D` (lag = disorder), every window in the retained band `[wm−D, wm)` is STILL receiving late tuples ⇒ HOT ⇒ **not spillable**. A window goes cold only after it ages PAST the lateness bound — but the whole band must be resident before the oldest ages out, so OOC hits the cap and OOMs BEFORE spilling can engage.
- **Proven:** lockstep (in-order, emit_lag=4M, N_w=80, pool=26k, cap=512) → OOC SURVIVES (spilled 73 slices, peak 512) while lag-honored in-mem OOMs (rc=137). Skew/out-of-order (emit_lag=D=4M, same N_w/pool/cap) → OOC OOMs with **0 slices spilled** (`ooc512_skew_Nw80`), identical to in-mem. The in-order band is COMPLETED⇒spillable; the out-of-order band is HOT⇒unspillable.
- **CORRECTED DESIGN (supersedes "emit_lag = D"):** decouple disorder from lag. Use a SMALL disorder `D` (windows go cold fast) and a LARGE `emit_lag L ≫ D`. Then `[wm−L, wm−D)` is cold-but-retained ⇒ SPILLABLE backlog (`(L−D)/W` windows); only `[wm−D, wm)` is hot. Physically: `D` = network disorder, `L−D` = slow-uplink emission backlog (the legit slow-consumer model). The lockstep ladder is the `D=0` instance and already validates it.
- **W-LEVER BACKFIRE (related):** you canNOT shrink the buffer pool below what spilling needs to OPERATE. At W=120k/D=6M/pool=15k both arms OOM'd (OOC spilled only 87 MB) — starving the pool to gain band-headroom kills spilling. Keep pool ≈ the working ladder size (≥~300 buffers/retained-window). See [[project-ooc-mechanics]], [[project-ooc-err-policy]].
- **Known-good RQ1 contrast config (cap=512, SD card):** lockstep `lagval.test`, W=50k, emit_lag=4M (N_w=80), pool=26000, soft60/hard120 ⇒ OOC survives; soft/hard=100000 (spiller never fires) ⇒ lag-honored in-mem OOMs.
- **BURSTY CASE — needs the RELEASE build (2026-06-07).** Added wide periodic bursts (`gen_skew.py --burst-period/--burst-width/--burst-amp`; note bursts must be WIDER than the jitter span D/W or jitter smears them, and File-source ignores row packing so only event-time cardinality spikes matter). THREE bursty configs at cap=512 all OOM'd OOC (`ooc512_burst_Nw80`, `ooc512_burst2_Nw80` [equal 151MB band], `ooc512_burst3_Nw60` [dense, smaller pool]) — spilling engaged each time (97–131 MB out) but couldn't hold under 512. ROOT CAUSE (rigid, not tuning): making in-mem OOM forces band >~160 MB, but OOC's UNSPILLABLE floor (debug base RSS ~195 MB + pool ~160 MB + hot band [the D-window frontier] + spill transients) already sits at ~512, leaving zero room for burst spikes. The steady (smooth) skew run survived at EXACTLY peak=512 (zero margin), so any burst transient ⇒ OOM. No debug config satisfies both "in-mem OOMs" AND "OOC survives bursts". ⇒ **positive bursty-survival result is a RELEASE-BUILD item** (smaller base RSS → real headroom). Smooth-load survival (steady skew + lockstep) IS demonstrated on debug.
