Quantitative model of the NES OOC (out-of-core spill) backend, measured in `.planning/eval-phase/lag-validation/` (see `FINDINGS-watermark-pool.md`, `calib-summary.csv`). For [[project-thesis-scope-anchor]].

**Measured constants (lockstep synthetic workload, ρ=1 distinct key/event-unit):**
- `ρ·e ≈ 39 bytes/key` — keyed state is linear in lag: `S_backlog = ρ·e·L`, window-size-independent.
- `floor ≈ 195 MB` — baseline resident (buffer-pool base + RocksDB wbuf 64 + cache 32 + runtime). Large relative to a 512 MB cap, so caps < ~512 are infeasible.
- Steady-state per-window overhead ≈ **1.2 MB/window**, **thread-independent** (attribution test: threads 1/2/4 → flat resident; more threads even *lowers* peak by parallelizing flush).
- Buffer pool: `POOL ≈ 300·N_w` (~300 buffers/window, buffer ≈ 8 KB) — pinned, **unspillable** retained-window bookkeeping. `N_w = emit_lag/window = L/W`. NES default pool is 32768 buffers (we'd been under-provisioning at 16000).

**The two failure modes (both NOT fixed by the watermark or by spilling the hashmap):**
- `rc=141` = buffer-pool exhaustion, gated by `N_w` (too few buffers for the retained-window count). Fixed by `POOL ∝ N_w` (config) — confirmed: at N_w=80, POOL=16k fails, 32k survives, across all watermark settings. Watermark is irrelevant to rc=141.
- `rc=137` = OS OOM at the **terminal-flush burst**: with `emit_lag = whole stream`, nothing emits during the run, the entire backlog re-materialises at end-of-stream. This was the killer. Fixed by **bounded emit_lag** (windows emit continuously as they age; only a small band flushes at termination) — and the terminal flush is largely a *finite-benchmark artifact* (real IoT streams never end).

**Break-even window size:** spill pays off only when spillable-keyed-per-window (`ρ·e·W`) exceeds the ~2.4 MB peak unspillable overhead/window → `W* ≈ 2.4MB/(ρe) ≈ 62 s` at ρ=1. 10k phase (100 s windows) worked; Nexmark (10 s) catastrophically didn't; Phase 2 (50 s) just below. So large windows are essential.

**Solution option set (RQ1 integration; thesis forbids JIT/codegen edits, host-side OK):**
- **A (config only, zero code):** bounded `emit_lag` + `POOL = 400·(L/W)`. Fixes both rc=141 and the terminal burst. **Try first — may make OOC work with NO code change.** Use large windows (W ≥ ~200 s) to keep `N_w` low.
- **D (small host change):** drop soft/hard watermarks, spill all cold + small LRU resident set. Cleaner policy; on this workload LRU≈FIFO (no recency locality), doesn't fix the floor — cleanup, not a fix.
- **Scaffold trims (config):** lower `max_number_of_buckets` (def 10000) / `page_size` (def 1024); buffer size is a construction constant.
- **B (large code change, AVOID unless needed):** reclaim the unspillable per-window bookkeeping in `DefaultTimeBasedSliceStore` — the only structural floor fix. User wants options aside from B.

**DEEPER STRUCTURAL FINDING (the key thesis insight):** could NEVER make spill-OFF OOM — in-memory backlog kept fitting (329→390→426MB) even at L=16M, because **continuous emit drains the retained band → with bounded lag the backlog stays bounded → fits in RAM → OOC not needed (in-memory wins)**. **⚠️ ROOT-CAUSE CORRECTION (2026-06-07) — the spill-ON overhead is NOT fixed RocksDB; it is NES unpooled-allocator chunk fragmentation that scales with N_w.** Traced in code, not just inferred:
- DIRECT MEASUREMENT: from the cap=1024 `p2` pairs (same workload, only spill on/off, NEITHER clamped), spill-ON's EXTRA over in-memory is a flat **~3.7 MB per retained window** (L=2M: 344−196=148MB over N_w=40; L=4M: 629−333=296MB over N_w=80 → 3.7MB/win both). And `p2_L2M_on`/`p2_L4M_on` had `spill_dir=0` (NO disk spill) yet still +148/+296MB → the cost is alloc churn, NOT RocksDB I/O. (The 512-cap rows do NOT measure overhead: peak=512 is the kill point, not true demand.)
- MECHANISM (code): HashMap pages + bucket dirs come from `BufferManager::getUnpooledBuffer` → `UnpooledChunksManager` (NOT the fixed pool). It is a BUMP allocator: `allocateSpace` only appends to the newest chunk (`lastAllocateChunkKey`); each chunk is pre-sized to ~10 buffers (`rollingAvg * NUM_PRE_ALLOCATED_CHUNKS=10`); `usedSize` is never decremented on free; a chunk is returned to the OS ONLY when ALL its segments drain (`activeMemorySegments==0`, UnpooledChunksManager.cpp:168). So one live retained-band page pins a whole ~10-page chunk, and spill→unspill churn (spill frees pages, unspill mallocs FRESH pages into a NEW chunk) strands pages across many frozen chunks → RSS ratchets up with N_w and never returns. In-memory build is append-friendly (pages born+freed together at GC) → less fragmentation → lower peak.
- RETRACTS the earlier "fixed ~180MB RocksDB wbuf+cache" diagnosis (recon_on_tiny at wbuf8/cache4 still OOMed — RocksDB buffers were a red herring, confirmed).
- FIX OPTIONS (structural / Option B, now precisely targeted): (1) route HashMap pages through the POOLED BufferManager (freed pages reused, not re-malloc'd) — cleanest "stop not-freeing" fix; (2) per-slice page freelist reused across spill/unspill (kill churn); (3) stream spilled blob straight to sink on emit (never re-materialize a full resident map — extend the existing 1/P streamWindowPartition path).
- INSTRUMENTATION ADDED (2026-06-07): file-static atomics in `UnpooledChunksManager.cpp` log a grep-stable `UPOOL` line (liveChunks, liveChunkBytes, liveActiveBytes, peakChunkBytes) on every chunk alloc/free. `run-cell.sh` reduces to a CELL_UPOOL summary in logs/<label>.log. (First version had a segment alloc/free accounting drift — fixed: segment bytes now counted in getUnpooledBuffer using alignedBufferSize, matching the free path.)

**⚠️ MECHANISM RE-CORRECTION (2026-06-07, from clean trace) — it is LIVE-PAGE DUPLICATION, not dead-space chunk fragmentation.** Trace: 2.5M tuples, W=50s, N_w=40, cap=1024, same workload, only spill on/off:
- spill-OFF: maxLiveActiveBytes=12.6MB, 965 chunks, slack 1.30×, RSS 336MB.
- spill-ON (P=4): maxLiveActiveBytes=81.1MB, 5884 chunks, slack 1.20×, RSS 515MB.
- KEY: within-chunk slack is only 1.2–1.3× (chunks ~80% FULL) → the overhead is NOT empty space pinned in undrainable chunks (my earlier framing — RETRACTED). Spill-ON physically holds **~6.4× more LIVE HashMap pages at peak** (12.6→81MB) for identical window state. The chunk-count 6× just tracks the live-page 6×.
- This still IS "data accumulated, not freed" (user's intuition holds) but via live duplication, not fragmentation slack.
- PRIME SUSPECT: the P=4 partitioned emit path — `materializeResidentPartition` (resident slices) and per-partition `deserialize` (spilled slices) build FRESH copies of a window's entries (split across P partition maps) at emit, ON TOP of the resident originals → transient ~2× per emitting window across the emit band. DISCRIMINATOR RUNNING: same cell at P=1 vs P=4; if P=1 collapses live-page count toward the off baseline, partitioned-emit copies are the cause. (NOTE: P=1 is a DIAGNOSTIC only — user rejects P=1 as a config since it defeats restore-streaming.)
- FIX, if confirmed: free each partition's source entries as they are streamed out instead of materializing all P copies before emit; or emit partitions one-at-a-time with the prior partition's copy released. Otherwise the pooled-allocation fix (route HashMap pages through the fixed pool) still bounds total RSS regardless.

**CODE LIFECYCLE FINDING (2026-06-07, read DefaultTimeBasedSliceStore.cpp + graphify-nav):** there is NO free-at-emit anywhere. A slice's maps (and their unpooled pages) are freed ONLY in `garbageCollectSlicesAndWindows` (DefaultTimeBasedSliceStore.cpp:212-272), gated `sliceEnd + windowSize < globalWatermark`; destructor runs at slicesToDelete.clear() (L271). `getTriggerableWindowSlices` (L105) only flips windows to EMITTED_TO_PROBE — frees nothing. So emitted slices linger until the watermark advances a full window past them, in BOTH modes. spill-ON layers a SECOND page generation per spilled slice: fill→spill(free)→unspill(fresh pages in a NEW chunk)→GC(free); chunk-granular freeing keeps both generations' chunks resident → the measured 6×.
**FIX (host-side, nes-physical-operators, no JIT):** release an emitted tumbling slice's maps AT EMIT instead of at watermark-GC → bounds resident set to (filling + emit batch) not (filling + whole retained band + unspilled 2nd-gen copies). Must respect the late-write/pinnedKeys window (Increment C) — safe for lockstep/no-late-data tumbling; in general free only past the emit-lag boundary. Alternative/orthogonal: route HashMap pages through the POOLED BufferManager (reuse, not re-malloc into fresh chunks) — bounds RSS regardless of churn.
**NOT yet pinned to certainty:** exact arithmetic of 6.4× LIVE bytes (vs 6× chunk count) needs a per-slice resident-lifetime counter (resident slice count + bytes over time). Fix direction does not depend on it.

**ARCHITECTURE CLARIFICATION (2026-06-07) — TWO buffer systems; the OOC POOL knob never bounded the state.** Resolves the recurring "why aren't we using the buffer manager" confusion:
- POOLED BufferManager: FIXED 8KB buffers (DEFAULT_BUFFER_SIZE=8*1024), count=`number_of_buffers_in_global_buffer_manager` (the POOL knob). Holds STREAMING TupleBuffers between operators. THIS is what the eval's POOL∝N_w sizing tuned and what rc=141 exhaustion was. Does NOT hold aggregation state.
- UNPOOLED chunk manager (UnpooledChunksManager): variable-size, heap, packs small allocs into ~10-buffer chunks. Holds the HashMap STATE — bucket dirs (~2KB) + data pages (1KB each). ChainedHashMap::insertEntry calls getUnpooledBuffer (ChainedHashMap.cpp:164,180). THIS is what OOMs (rc=137) and what spill targets.
- HashMap-on-unpooled is UPSTREAM NES design (vendored, predates the OOC spill work), NOT an OOC choice. Reason: page=1KB but pooled buffer=fixed 8KB → pooled wastes 8×/page; and unbounded live-map count would exhaust the fixed pool. So NES uses a variable-size PACKING allocator for growable state.
- Defaults: page_size=DEFAULT_PAGED_VECTOR_SIZE=1024; hashmap numberOfBuckets=conf.numberOfPartitions=DEFAULT_NUMBER_OF_PARTITIONS_DATASTRUCTURES=100 (NOT max_number_of_buckets=10000, which is a different unused-here knob) → calcCapacity(100,0.75)→256 chains → ~2KB bucket dir/map. Pooled getBufferBlocking() takes no size (fixed 8KB).
- CONSEQUENCE: aggregation state was NEVER pool-bounded — that is precisely WHY OOC spill exists (bound it by moving cold maps to RocksDB). The measured bug: the unpooled packer is BUMP-ONLY with whole-chunk free (no intra-chunk reuse; frees only when ALL segments drain), so spill/unspill churn fragments it.
- FIX OPTIONS RE-SCOPED: (#2 "route pages through pooled BufferManager" as I'd phrased it is NAIVE — 8KB buffers for 1KB pages = 8× waste, or re-implements the packer). REAL #2 = make UnpooledChunksManager reuse freed segments within a chunk (freelist) instead of bump-only. #1 = free-at-emit (smallest, most direct attack on churn).

**OPTION-1 (free-at-emit) FEASIBILITY — BLOCKED as conceived (2026-06-07, code read).** Aggregation emit does NOT copy aggregates out: triggerSlices stores RAW non-owning pointers to the slice's per-worker HashMaps (AggregationOperatorHandler.cpp:104-105) into EmittedAggregationWindow.allHashMapPtrs (L191), dispatched to the probe via the task queue (L194) and drained ASYNC. So freeing a slice's maps at trigger = use-after-free (this is the emittedKeys "async-probe-drain invariant"). Also: free-at-emit targets the wrong thing — the dominant resident is the PRE-EMIT lag band (completed, not-yet-emitted), which by definition can't be freed at emit; only the brief emit→GC lingering is reclaimable, already bounded by probe-drain + watermark GC (GC uses a SEPARATE probe-side watermark, WindowBasedOperatorHandler.cpp:59-70).
